# B-Box 实体交互游戏控制器

> 一个 IMU 姿态驱动的实体推箱子游戏控制器。
> 你不需要手柄，不需要屏幕——拿起这个盒子，
> 推、翻、倾斜，角色就动。震你一下，你就知道它懂了。

---

## 1. 项目概述

B-Box 是一个基于 **ESP32-S3 + MPU6050 IMU** 的实体交互控制器。玩家通过物理动作（推动、倾斜、翻转）来控制 Unity 推箱子游戏（A-Box）中的角色，并获得电机震动的即时物理反馈。

最核心的想法其实很朴素：**如果推箱子游戏真的可以"推"一个箱子，会怎么样？**

### 1.1 一句话

**把物理世界的手势，变成了游戏里的操作。** 推一下就是走一步，翻过来就是撤销，扣住不放就是重置。不依赖屏幕提示，不依赖按键记忆——手感即界面。

### 1.2 系统架构

```
┌─────────────────────┐         ESP-NOW          ┌──────────────────────┐
│  A 板 箱子端        │ ◄──────────────────────► │  B 板 桥接端          │
│  MPU6050 IMU        │    EVT/HEARTBEAT/IMUQ →   │  USB CDC → PC/Unity  │
│  手势识别 + 电机     │    ← ACK/HAPTIC/STATE     │  协议过滤转发         │
└─────────────────────┘                           └──────────┬───────────┘
                                                             │ USB CDC
                                                    ┌────────┴───────────┐
                                                    │  PC / Unity A-Box   │
                                                    │  推箱子游戏          │
                                                    └──────────────────────┘
```

- **A 板（箱子端）**：ESP32-S3 + MPU6050，负责原始传感器采样、Mahony 互补滤波姿态解算、手势识别、电机反馈
- **B 板（桥接端）**：ESP32-S3，负责 ESP-NOW 无线接收、协议行过滤、USB 串口透传到 PC
- **A-Box（Unity）**：推箱子游戏逻辑 + Web 前端调试面板，接收标准文本协议控制角色

## 2. 核心技术亮点

### 2.1 姿态不敏感的推动检测

最开始我们直接比较传感器轴的加速度：Y 轴正半轴大就是向前推。这在盒子上电时平放的情况下勉强能用——直到玩家把盒子换了个姿势。

就像一个闹钟，你把它转 90 度之后，"向上"还是指天花板，但"向前"已经不是盒子的箭头方向了。这个问题折磨了我们好几天：推前有时候出左，推左有时候出后。每次调整阈值都像是在和物理定律讨价还价。

最终的解决方案出奇的优雅：**Mahony 互补滤波 → 四元数倾斜补偿 → 去 yaw → 机体航向系判向**。简单说，就是用四元数算出"地心在哪"，然后把加速度旋转回水平面，再用盒子自身的坐标系去判断方向。无论你横着放、竖着放、斜着放——前永远是盒体箭头方向。

```
传感器加速度 → quatRotateWorld（转到世界帧）
            → deYawHorizontal（去掉yaw，锚定机体轴）
            → 高通滤波去DC → 过阈值峰值捕获 → 向量最大分量判向
```

- 峰值捕获窗：120ms 内追踪最强样本，一次物理推动 = 恰好一条 EVT
- 回摆抑制：推完手回位那一瞬间的反向加速度，会不会被误判成反方向？不会。
- 再武装迟滞：信号必须真的安静下来才能再次触发——就像一个真正的人在说"我准备好了"

### 2.2 分层手势交互系统

用手势控制游戏，最大的坑是手势之间互相干扰。倾斜 45° 和翻面 110° 在传感器眼里只是数字不同，但在玩家眼里是完全不同的两个动作——一个是在玩弹珠，一个是想重置游戏。

我们的做法是把角度切出明确的区间，每个区间只做一件事：

| 角度范围 | 持续时间 | 触发 | 语义 |
|---|---|---|---|
| < 45° | — | — | 正常游戏，随便晃 |
| 45°–90° | 3s | MARBLE_ENTER/EXIT | 像端盘子一样斜着，3秒后进入弹珠 |
| 90°→110°→回落 | < 0.5s | UNDO | 快速翻一下立刻回来，像翻书页 |
| > 110° | 2s | RESET | 扣住不放，两秒后重置 |

翻面撤销这个手势的直觉来源很简单——"做错了？翻篇。"

实际操作时你会发现，快速翻一下和长时间扣住，手势的节奏感非常不同。代码层面只是一个 500ms vs 2000ms 的差异，但手感上完全是两个世界。这就是物理交互有趣的地方：时间本身成了一个输入维度。

### 2.3 持续状态替代离散事件

倾斜最初也像推动一样做成"触发一次→等待回正→再触发"的离散事件。但弹珠模式需要的是持续的倾斜角度来驱动物理模拟——你不能让弹珠每收到一个"倾斜事件"才动一下。

改成 **TILTS 持续状态消息**，与 IMUQ 四元数同频 20Hz 上报。宿主侧每 50ms 就能拿到一次当前的 pitch/roll，弹珠可以平滑滚动，就像你真的在倾盘子让玻璃珠滑动。

这个改动看似简单——不过是从"发事件"改成"发状态"——但背后的思维转变很重要：**手势不是一个点击，而是一种姿势**。

### 2.4 非阻塞实时电机反馈

手势触发后震一下确认，这是实体交互的"OK 提示音"——你不能盯着屏幕看是不是收到了，你得感觉到。

电机用 LEDC PWM 驱动，255 最大力度。所有反馈统一用这个强度——不搞"弱震动提示"和"强震动警告"的区分，因为在嘈杂环境下你分辨不出来。**震，就震到底。**

计时器是非阻塞的：`motorEndMs = millis() + duration`，loop 末尾检查超时关闭。不影响 200Hz 的 IMU 采样循环。简单到一行代码就能明白，可靠到不会因为震动卡住传感器。

### 2.5 双板无线 MAC 对传

为什么不直接在箱子上接 USB 线给电脑？因为**线会限制手势**。你不可能在被一根 USB 线拽着的情况下自由翻转盒子。

所以用了两块板：A 板放在箱子里（电池供电），B 板插电脑上当无线网卡。ESP-NOW 点对点，MAC 地址编译期写死，不需要配网、不需要握手、上电即通。B 板每 5 秒报告一次链路统计——收到了多少帧、丢了几个、拦了多少外来干扰。

当第一次看到 B 板串口吐出 A 板的 IMUQ 数据时，那种"两块板真的在隔空聊天"的感觉是调试过程中最快乐的瞬间。

## 3. 调试与工程实践亮点

### 3.1 Web 前端实时调试面板

Unity 项目打开慢、编译久、需要配场景。调手势参数的时候，我们更需要的是一块能秒开的仪表盘。

于是有了这个 Web 面板：Chrome 打开，Web Serial API 直连 COM 口，实时查看所有上行消息。不需要 Unity，不需要编译，改一行 JS 刷新浏览器就能看到效果。

- 消息流实时显示，按 TYPE 过滤（翻数据流的时候，可以一键关掉 IMUQ 的刷屏）
- 推动方向罗盘：Canvas 2D 实时画动态矢量 + 阈值圈 + 判定方向——**你推一下盒子，罗盘上的箭头就跳一下**
- 姿态立方体：CSS 3D 渲染四元数姿态，盒子怎么转它就怎么转
- 自动 ACK：这个问题烦了我们很久——板子发出 EVT 后如果没收到 ACK，会在 300ms 后重传，最多 5 次。6 条相同的 EVT 刷屏。加了两行代码自动回 ACK，世界清净了
- UNKNOWN 数据默认隐藏——开着也看不懂，但需要调试的时候可以手动打开

### 3.2 脏帧溯源

曾经一度有神秘数据出现在串口：`UNKNOWN 64,0.50,33108`。不是 EVT，不是 IMUQ，不是 TILTS。它在 Web 面板上反复出现，像一个幽灵。

排查过程：检查了 A 板所有 `snprintf` 格式（全部带 TYPE 前缀）、检查了 B 板 isProtocolLine（全部大写开头）、检查了 ESP-NOW 源 MAC 过滤（配置正确）、甚至怀疑 Web 前端的行分割有问题。最后在 B 板加了 `DBG,JUNK` 调试输出——遇到非协议行时直接打印原始内容。结果 `dropped=0`，一个脏帧都没有。

**幽灵不存在。** 问题是 Web 前端把两个正常行拼成一行了。串口 readline 的缓冲区刚好在行边界断开，下一段数据的开头不是合法 TYPE，就被标成了 UNKNOWN。

整个过程大概花了两小时排查，结论只需要改几行代码。但那种"终于抓住幽灵了"的感觉——**这就是嵌入式调试最上头的地方**。

### 3.3 协议驱动开发

当固件（C++）、Unity（C#）、Web（TypeScript）三个代码库要吃同一套通信协议时，最怕的就是"我以为你发的是这个"vs"我以为你收的是那个"。

我们的解法很直接：**以 PROTOCOL.md 为单一事实来源**。所有新增消息类型，先在协议文档里写清楚格式和字段含义，然后在三个地方照着实现。协议设计本身也留了后路——未知 TYPE 回 NAK 不崩溃，多余字段直接忽略——所以迭代起来不用每次改协议就三边同步上线。

### 3.4 手势阈值的调参过程

调参这件事，理论和手感之间的差距大得惊人。

推动阈值从 0.25g 降到 0.18g（"轻轻推就动"），又升回 0.20g（"太灵敏了走路都触发"）。翻面阈值从 80° 调到 110°（"扣盒子要扣很深才触发 RESET，防止和弹珠的 45°-90° 重叠"）。弹珠保持时间从 2 秒改成 3 秒（"两秒太短了，正在犹豫要不要进去它就进去了"）。

每一次调整都是连着 Web 面板看实时数据，推一下、看波形、改参数、烧录、再推。没有"最佳值"——只有"在这个盒子上，以这个力度推，大多数人不会误触，也不会觉得太费力"。

## 4. 混合方案探索：戒指 SDK

IMU 手势的天然局限是：有些动作无论怎么设计，误判率都不低。旋转三圈做撤销？摇三下做切换？我们都试过，最后都扔掉了。**不是说技术上做不出来，是说"要求玩家记住这个手势"这件事本身就违背了直觉交互的初衷。**

于是我们留了一条后路：智能戒指。

在 Unity 的 `InputHub` 中，戒指输入通道（UDP）和 B-Box 输入通道（串口）是平行的。它们最后都变成 `GameCommand` 或 `Tilt` 向量，游戏逻辑层不关心信号从哪来。

**分工设想**：
- B-Box 做**连续姿态输入**——推动走格子、倾斜弹弹珠。发挥 IMU 200Hz 采样率的优势
- 戒指做**离散命令触发**——确认、撤销、重置。发挥物理按键零误判的优势
- 两种设备同时操作时，InputHub 按先到先得或优先级处理

当前状态：UDP 通道和事件映射已预留，戒指 SDK 接入即可打通。但我们心里有数——**最好的交互可能是两者的混合，而不是非此即彼。**

## 5. 技术栈

| 层 | 技术 |
|---|---|
| 固件 | C++ (Arduino), ESP32-S3, MPU6050, ESP-NOW, LEDC PWM |
| 姿态解算 | Mahony 互补滤波, 四元数 |
| 无线通信 | ESP-NOW 点对点单播, MAC 白名单编译期绑定, 信道锁定 |
| 串口协议 | 纯文本行协议 (ASCII, 逗号分隔, 115200 8N1) |
| Unity | C#, Web Serial, GameController 架构 |
| 调试面板 | TypeScript, Vite, Web Serial API, Canvas 2D, CSS 3D |
| 桥接 | Python (esp32_bridge.py), UDP |
